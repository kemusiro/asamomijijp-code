# asamomijijp-code 運用方針

## 1. 目的

このリポジトリは、`asamomiji.jp`の記事に付随する公開用ソースコードを管理する。対象には、記事作成時のサンプル、複数ファイルからなる実行・検証可能なコード、過去にGitで管理されていなかった自作プログラムを含む。

サイトの本文、画像、レイアウト、移行台帳は`asamomijijp-site`で管理し、完全なコード一式は原則として本リポジトリで管理する。

## 2. 配置基準

| 対象 | 配置先 |
| --- | --- |
| 説明に必要な短いコード抜粋 | `asamomijijp-site`の記事Markdown |
| 複数ファイル、ビルド可能な完全版、ダウンロード対象 | 本リポジトリの`projects/<article-slug>/` |
| 原版アーカイブ、JAR、ファームウェアなどの配布物 | 必要性と安全性を確認後、GitHub Releases |
| 独立した開発・リリース・Issue管理が必要になったもの | 所有者承認後に個別リポジトリへ分離 |

記事中の抜粋と完全版が重複する場合は、公開時に内容を照合する。本サイトのビルドはこのリポジトリに依存させず、Git submoduleも使用しない。

## 3. ディレクトリ構成

各記事付属プロジェクトは次を基本とする。

```text
projects/<article-slug>/
├─ README.md
├─ src/
├─ examples/        # 必要な場合
├─ tests/           # 必要な場合
└─ THIRD_PARTY_NOTICES.md  # 第三者要素がある場合
```

プロジェクトREADMEには、対応記事、概要、原作成時期、Git収録日、動作環境または当時の環境、検証結果、既知の制約、ライセンス例外、原資料と変換後のハッシュを必要に応じて記載する。

## 4. 履歴と版の扱い

- Git導入以前の履歴を推測で作成せず、コミット日時を過去へ改変しない。
- 原作成日や旧公開日はREADMEの来歴として記録する。
- 記事公開時点のコードにタグを付けるかコミットSHAを記録し、記事から不変の参照先へリンクする。
- タグ名はプロジェクト名を含める。例: `mml-player/article-2026-08`。
- その後の修正は別コミットとし、歴史的原版と現行修正版を混同しない。

## 5. ライセンス

所有者が作成して本リポジトリで公開するコードは、個別の明示がない限り、ルート`LICENSE`のBSD-2-Clauseに従う。

- ソース内の著作者表示、著作権表示、ライセンス表示を保持する。
- 別ライセンスを適用するプロジェクトは、そのディレクトリで明示する。
- 第三者コードや資料は、元のライセンスと表示条件を確認し、必要に応じて`THIRD_PARTY_NOTICES.md`へ記録する。
- 権利関係が未確認のものは公開しない。

## 6. 歴史的コード

- 原本アーカイブはGit管理外で保存し、ファイル名とSHA-256を記録する。
- Gitへ収録するテキストはUTF-8を標準とする。文字コード変換は機械的変更として記録し、可能な限り往復一致を確認する。
- コンパイルできたことと、現行環境で安全・正常に動作することを区別する。
- 古いAPI、サポート終了環境、既知の警告、未検証部分をREADMEと記事に明記する。
- 未検査の旧バイナリは実行・配布しない。

## 7. Releaseの扱い

GitHub Releaseは、原版アーカイブやビルド済み配布物を読者へ提供する必要がある場合に限って使用する。Release作成前に次を確認する。

1. 配布権と第三者ライセンス
2. 秘密情報、個人情報、不要なメタデータ
3. アーカイブのパス安全性と内容
4. マルウェア・不審な実行物の有無
5. SHA-256、ビルド環境、動作確認範囲
6. サポート対象か、歴史的資料としての無保証公開か

Release作成とバイナリ公開は所有者の明示承認後に行う。

## 8. 公開前確認

各プロジェクトは、該当する範囲で次を確認する。

- 著作者、ライセンス、第三者要素
- 秘密情報、個人情報、ハードコードされた認証情報
- 原本と公開用コピーの対応
- ビルド、静的検査、テスト、実機確認の別
- 記事内コードとの一致
- READMEの環境・制約・無保証表示
- 記事からタグまたはコミットへの固定リンク

## 9. 変更管理

コミット、push、Release、リポジトリ設定変更、公開済み履歴の書き換えは、対象と影響を確認してから実施する。`asamomijijp-site`と本リポジトリの変更は別コミットで管理し、片方の公開失敗が他方のビルドや公開を妨げない構成を維持する。
