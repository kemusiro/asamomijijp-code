# Rev Cの最終目標とYs II再生への移行

2026-11-13。ユーザーが示したRev Cのゴールは、WebLabで演奏できた
Ys II「TO MAKE THE END OF BATTLE」を、実際のYM2203Cとライン出力で全曲再生すること。
現在までのI2C・USB-MIDI初期受入完了は、そのための基板・信号経路の確認段階と位置づける。
Ys IIの実機再生は未実装・未検証。

## 手元のデータで確認した要求

Git管理対象外の既存WYM1全曲データを検査した。楽曲データを配布物へ追加しない。

| 項目 | 値 |
| --- | ---: |
| イベント数（末尾の追加消音6件を含む） | 123,137 |
| 周期（末尾待ち500 msを含む） | 298,218 ms |
| ファイルサイズ | 738,838 bytes |
| クロック | 4 MHz |
| 平均レジスタ書き込み数 | 約412.91回/秒 |
| 最大の1秒窓内イベント数 | 569 |
| 同一msの最大件数 | 93（先頭0 ms） |
| 先頭0 msを除く同一msの最大件数 | 17 |

入力SHA-256：`d7b6846c7515237ee6c7a7c785d03769e923433f8f9c4652482f7ee25fc8e853`。
WYM1ヘッダー・長さ・時刻順・期間内であることを検査し、全イベントを現行の
`valid_register()`へ通した結果、禁止されるレジスタ値の組み合わせは0件だった。
密度は時刻が窓の右端を含む `(end-width,end]` に入る件数で算出した。
これは静的解析であり、実機の処理速度や音質を測定したものではない。

## 現行版の制約

1. 音源側は11.25 msの音声ブロックごとにYMへ最大1書き込み。
   理想条件でも約88.89回/秒。平均要求だけで約4.65倍の不足がある。
2. HOSTの現行コマンドはACK確認前に40 ms待ち、PUSHは2イベントずつ。
   ACKが最初の確認で返る理想条件でも約50イベント/秒が上限。
   通信・状態確認・Python処理などはさらに加わる。
3. 検証用10 kHz I2Cでは、PUSHの17バイトとアドレスだけで
   2イベント当たり162クロック（9ビット×18）を必要とする。
   COMMIT・ACK読取り・待ちを無視しても約123.46イベント/秒が上限。
   曲の平均密度を運ぶだけでPUSH部分に約33.45 kbit/sが必要。

したがって、現行版のままでの全曲再生は処理能力の下限比較で成立しない。
キュー容量だけを増やしても、曲を遅く流しても、本来の演奏時刻を保った解決にならない。
一方、この結果はMicroPython自体の限界を測ったものではない。
現在の保守的な音声ブロック処理・GPIO操作・コマンド形式の組み合わせの制約である。

## 次の実装方針

音源側Pico 2はC/C++ SDKによる別ファームウェアを主案とする。
操作側PicoのMicroPythonは継続可能だが、高速転送時の実測で確認する。
MicroPython現行版と受入済みZIPは復帰用に保存する。

- 承認済みGPIO、Rev C基板、音声経路を維持する。
- PIO/DMAによるFM受信とI2S出力、既存FM復号・利得・出力上限をC版へ移す。
- 音声処理とµs時刻のYMレジスタ実行を、USB/I2C解析から分離する。
  コア分担と割り込み優先度は、資源割当と最悪処理時間を確認して決める。
- YMのBUSYとデータバス方向切替のタイミングを守り、1書き込み/11.25 msという
  制限を外す。チップ自身の受理能力と同時刻バーストは実測する。
- WYM1のレジスタ値と順序を保持する。MIDIノートへの変換やイベント間引きは行わない。
  元のWYM1はms単位で丸め済みのため、元VGMのサンプル時刻精度を復元したとは扱わない。
- 受信キューは時刻付きのブロック転送・先読み・空き量通知に対応させる。
  既存のv1プロトコルを黙って置換せず、高速方式はバージョンを分けて文書化する。
  I2Cは100/400 kHzを候補とし、プルアップ・配線・実効補充速度を実機確認して採用する。
- USB-MIDIは演奏用として維持する。Ys IIのレジスタ列は専用データ経路を使う。
- C版はMicroPythonのREPLを提供しない。CDCログ/制御とUF2書き込みを用意する。
  操作側PicoをThonnyで使う構成は維持できる。

C SDKはPIO、DMA、タイマー、I2C、割り込み、マルチコアを利用できる。
詳細は[Raspberry Pi公式ハードウェアAPI](https://www.raspberrypi.com/documentation/pico-sdk/hardware.html)と
[高水準API](https://www.raspberrypi.com/documentation/pico-sdk/high_level.html)を参照する。
SDK/ツールチェーンの版とコミットはC版の導入時に固定する。

## 実装・受入の順序

1. **C版の音声経路とバス処理**：無音起動、SSG、FM→PCM→I2S、消音を少数の確認へまとめる。
   既存試験全件を再実行するのではなく、移植で変わった経路を検証する。
2. **同じYs II BINのローカル再生**：通信速度の問題と音源処理能力を分離する。
   738,838 bytesはPico 2のRAM全体より大きいため、全曲をRAMへ展開しない。
   専用フラッシュ領域から読んで先読みし、再生中はフラッシュの消去・書込みをしない。
   曲を含むテストUF2/資産はGit管理対象外に置く。メモリマップと転送手順は実装時に確定する。
3. **外部I2Cからの補充式再生**：操作側MicroPythonでBINを読み、高速ブロック転送する。
   全曲保持せず、音源側キューの枯渇・順序・CRC・STOP・通信断を検証する。
4. **全曲の実機受入**：123,137イベントの順序、曲長、欠落/重複、実行遅延分布、
   キュー下限、音声DMA異常/バッファ不足、左右の音、歪み、終端消音を確認する。

初期化93件を含む同時刻書込みは物理的には逐次実行になる。
先頭の無音準備と演奏開始基準を定義し、以降の同時刻群も順序と実行遅延を記録する。
具体的な許容遅延はYMバス処理の測定後、全曲受入前に決める。
WYM1の元データが持たない精度や、全バーストの完全同時実行は保証しない。

この順序で、まず「Rev Cが同じ曲データを全曲処理できる」ことを成立させ、
次に「操作側MicroPythonから補充して同じ曲を演奏できる」ことを最終確認する。
